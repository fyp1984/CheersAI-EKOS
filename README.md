# EKOS · 企业知识库操作系统

> **EKOS（Enterprise Knowledge OS）** 把散落在各个系统、每个人、各种格式里的知识，变成 AI 能直接调用、企业能治理、组织能沉淀的资产。

## 一、这是什么

企业从来不缺文档，缺的是**能被 AI 直接调用的知识层**。

绝大多数企业的 AI 落地卡在同一个地方：知识还按“给人看”的方式堆在网盘、即时通信和 OA 里——格式各异、版本混乱、权限不清。模型再强，接不上这些存量数据，也只能空转。

EKOS 补的就是这一层。它把企业知识从“文档”变成“资产”：

- **接得进来**——跨平台自动归集，不靠人工上传；
- **管得住**——权限、脱敏、知情同意、审计，在知识入库那一刻就开始生效；
- **用得起来**——一个自然语言入口，AI 直接调用，回答必带出处；
- **留得下来**——知识对象化、版本治理、复用可追踪，经验不随人走。

一句话：**EKOS 是企业的知识操作系统——不是又一个“能问答的文档库”。**

## 二、产品理念

### 2.1 一条认知纠偏

> **知识库的第一服务对象是 AI，不是人。**

这是 EKOS 与市面上绝大多数知识库工具的根本分野。

数字化时代，知识库是**给人看**的：上传文档、人工维护、检索给人读。而在 AI 时代，文档体量在涨、版本迭代在快，真正高频阅读这些知识的其实是 AI——**人只是知识的来源与受益者，AI 才是知识的第一消费者。**

很多企业用 AI “用不顺手”，根子就在这里：知识仍按“给人看”的方式堆在文档里，AI 接不上企业零散的存量数据。

### 2.2 两条产品铁律

从上面那条认知，直接推出两条必须落到产品默认行为里的铁律：

| 铁律 | 含义 |
|---|---|
| **入库即格式化** | 所有非结构化、多版式的文本统一转为 Markdown，并完成分词与向量化；图片、视频完成 OCR、切片、向量化。这是“AI 可读”的前提。 |
| **维护即动态** | 知识库不是静态仓库。AI 产出的新内容、对话记录、用户身份、角色定义、技能配置等**动态信息**，都应纳入知识库体系并自动回流，形成持续增强的闭环。 |

### 2.3 一个理论类比：知识时代的 DBMS

早期数据库软件把非结构化数据变成结构化数据，长出了成熟的 **DBMS**（数据库管理系统）。EKOS 做的是同一件事，只是对象换成了企业知识。

- **知识对象建模**——定义实体、关系、页面与流程要素，把散落信息拆成标准化知识对象，类比数据库的 DDL；
- **统一自然语言调用（K-NLQ）**——用户与 Agent 只表达意图，后端按内容结构自动路由到 SQL、向量或混合检索。**入口是自然语言，不是 SQL。**

如果说 CRM / ERP 管理的是“业务数据”，那么 **EKOS 管理的是“企业知识”**。

### 2.4 差异化在哪里

高合规行业的真实诉求是“既要 AI 用得上知识，又要数据出不了域、敏感信息不能裸奔”。前半段由成熟开源底座低成本解决，后半段由内容脱敏内核与私有化部署解决——两者叠加的这一段，恰恰是通用 RAG 引擎不做、办公生态内平台不便做的空白带。

> **EKOS = 开源版 Glean 的能力底座 + 面向 AI 的内容脱敏内核 + AI 行为护栏 + 私有化合规 + 中文企业纵深**

| 维度 | 品类通用做法 | EKOS |
|---|---|---|
| 服务对象 | 人 | **AI（第一服务对象）** |
| 能力底座 | 自研积累或闭源订阅 | **继承成熟开源组件**，把功能做全、把单价打下来 |
| 安全内核 | 权限镜像：能看 / 不能看 | **内容脱敏：能看，但被脱敏**——把安全从访问控制推进到内容层 |
| 治理深度 | 基础权限 | 准入四道门 + 脱敏出域 + 版本治理 + 安全检测 + 全量审计 |
| 质量评测 | 行业普遍缺失 | 题库 + 标准答案 + 错误归因 + 发布门禁 |
| 资产化 | 无 | 资产工厂 + 复用追踪 |
| 部署形态 | SaaS 为主，或绑定单一办公生态 | **私有化优先、数据不出域**，按数据敏感度分级部署 |
| 生态立场 | 绑定某一办公套件或云厂商 | **跨平台中立** |
| 语言与合规 | 英文原生、海外合规体系 | **中文企业纵深 + 国内合规资质路径** |

## 三、产品架构

EKOS 用两套分层描述自己，二者**互为正交**：一套回答“知识流过哪几站”，一套回答“代码和组件怎么摆”。

### 3.1 业务架构：知识生命周期四层架构

按知识的全生命周期分为**采集层 → 治理层 → 资产层 → 消费层**，类比图书馆的管理模型。

| 层 | 做什么 | 图书馆类比 |
|---|---|---|
| **采集层** | 归集一切知识，含动态信息与多模态文件 | 采购 |
| **治理层** | 让企业敢用、信得过：权限、脱敏、知情同意、审计 | 编目与审校 |
| **资产层** | 把知识变成组织能力：知识对象化、冷热分层、过期归档 | 上架馆藏 |
| **消费层** | 让知识被用起来、转出去：检索、问答、工作台、分发 | 借阅流通 |

### 3.2 技术架构：技术五层架构

```
┌────────────────────────────────────────────────────────────────────┐
│ L5 接入层    OpenAPI · MCP Server · Web SDK · K-NLQ                │
├────────────────────────────────────────────────────────────────────┤
│ L4 编排层    知识流水线（可编排）· 事件总线 · 任务调度 · 评测编排  │
├────────────────────────────────────────────────────────────────────┤
│ L3 内核层    自研差异化：跨源权限继承编排 · 知情同意门 ·           │
│              脱敏网关 · 分级出域 · 生命周期治理                    │
├────────────────────────────────────────────────────────────────────┤
│ L2 适配层    自研薄封装，所有外部能力都过这一层：                  │
│              连接器 / 解析 / 检索 / 模型 / 脱敏 / 评测 / 策略      │
│              各适配器 + 注册中心 + 配置装配                        │
├────────────────────────────────────────────────────────────────────┤
│ L1 底座层    开源与自有组件（可整体替换）：                        │
│              应用与图谱 · 国内连接器与深度解析 · 向量库 · 关键词库 │
│              OCR · 自动评测 · 模型路由 · 权限引擎 · 策略引擎       │
│              CheersAI Vault（内容脱敏，自有）                      │
└────────────────────────────────────────────────────────────────────┘
```

**两条边界：**

- **开源与自研之间**靠 L2 适配层隔离——底座的组件会换，差异化的内核不会变，中间夹一层适配器，换底座时上层无感；
- **能力与流程之间**分开——能力是零件（L1–L3），流程可编排（L4）。

**为什么这么设计：** 底座层的开源软件今天用一个、明天可能换另一个。EKOS 的立场是**不 fork、不改上游**，一律通过 API、适配器与配置扩展——上游能独立升级，我们不被拖死。自研只集中在开源不做、巨头不便做的一段：治理与合规。

### 3.3 数据流：知识处理的七步闭环

知识从进入系统到能被 AI 使用，走一条七步链路：

| 步 | 环节 | 做什么 |
|---|---|---|
| 1 | **连接** | 从飞书 / 钉钉 / 企业微信 / 本地文档库自动拉取，权限信息一并带过来 |
| 2 | **深度解析与沉淀** | 扫描件、表格、图文 PDF 统一转成 Markdown + 向量 + 元数据 |
| 3 | **三索引检索** | 关键词、向量、知识图谱三路召回后融合排序 |
| 4 | **证据链问答** | 每个回答都带出处；无据可依时明确拒答并说明原因 |
| 5 | **最小治理** | 入库范围授权 + 角色权限 + 全量留痕 |
| 6 | **内容脱敏** | 入库与出域两个环节都调用 Vault，完成敏感信息识别与脱敏 |
| 7 | **动态回流** | AI 产出的内容自动格式化入库，重新进入可检索范围 |

## 四、功能规划

功能分三个阶段推进：先把知识处理的主链路跑通，再做小团队可自助部署的产品化，最后补齐企业级治理。

| 阶段 | 侧重 | 能力 |
|---|---|---|
| **第一阶段**<br>跑通主链路 | 让知识接得进来、找得到、有出处、脱得干净 | 国内平台连接器自动同步 · 深度解析与入库规范化 · 三索引检索（关键词 + 向量 + 图谱）· 带证据链的问答与拒答护栏 · 基础权限与全量审计 · 入库授权与知情同意门 · 内容脱敏（对接 CheersAI Vault）· 对话产出动态回流 · 自动评测 · 外部可信知识源接入 |
| **第二阶段**<br>小团队可自助部署 | 面向小企业与小团队，开箱即用 | 准入四道门 · 数据分级与出域管控 · 版本治理 · 知识对象化 · 上下文工作台 · 防废墟运营机制 · 多模态（视频 / 图片）全链路处理 · 有效期自动下架 · 小团队上下文与记忆共享 |
| **第三阶段**<br>企业级治理 | 面向大集团与高合规行业，补齐重治理能力 | 资产工厂 · 多 Agent 与技能封装及融合 · 准入安全检测 · 分发中枢 · 知识对象建模（类 DDL）· 统一自然语言调用（自然语言入口，后端自动路由）· 数据平台对接 · 运行态协同（跨终端任务交接与多智能体协同） |

各阶段共同的能力边界：

- 数据源覆盖国内平台与本地文档库；
- 不绑定特定大模型，支持自托管与商业模型；
- 专注知识治理，不做通用应用开发平台。

## 五、工程结构

```

├── apps/                   应用层
│   ├── api/                对外 API 服务

│   ├── common/             日志与通用设施
│   ├── document/           文档解析、入库与规范化
│   ├── retrieval/          检索服务
│   ├── modelgw/            模型网关（统一的模型调用契约）
│   ├── vault/              内容脱敏适配器（对接 CheersAI Vault）
│   └── report/             报告编排
├── configs/                配置层：行业与场景差异落在这里
│   ├── aliases.yaml        术语与别名表

│   └── runtime.yaml        运行参数
├── deploy/                 部署
│   ├── compose/            本地开发编排
│   ├── scripts/            启动与备份脚本
│   └── fixtures/           合成样本（真实数据一律不入库）
├── tools/gate/             工程门禁：检查规则与执行脚本
├── tests/                  测试金字塔
│   ├── unit/               单元测试
│   ├── contract/           契约测试
│   ├── integration/        集成测试
│   └── golden/             Golden Test
├── external/               外部制品仓（模型权重、镜像、安装包，不入 git）
├── Makefile                统一命令入口
└── pyproject.toml          依赖与工具链配置
```

### 五条工程纪律

1. **内核层不出现任何行业术语。** 行业特有的字段、术语与流程一律落在配置层与提示词层。判断标准只有一句话——“如果换成一家医院用这套系统，这行代码要不要改？”**要改，就说明它不该在内核层。** 这条纪律是本仓库有能力同时支撑多个行业实例的前提。
2. **语种不写死。** 中文优先，但语种、地区、组织等变量都从配置读取，不硬编码进代码。
3. **不 fork、不改上游。** 开源组件通过适配器集成，不复制代码进主仓，保证上游可独立升级。
4. **依赖版本全部锁死。** 运行时依赖与开发工具链都写死具体版本，不用范围约束。环境必须可复现——否则今天的测试通过，说明不了明天的问题。
5. **门禁不可放宽。** 工程门禁由一个统一的标准文件定义，所有检查以它为准。为通过而放宽标准，等于取消门禁。

## 六、快速开始

环境要求：**Python 3.11.10**（版本冻结，不得放宽）、Docker、[uv](https://github.com/astral-sh/uv)。

```bash
git clone <仓库地址>
cd CheersAI-EKOS

# 建虚拟环境并装齐依赖
make setup

# 提交前必跑：静态检查 + 类型检查 + 单元测试 + 契约测试 + 门禁常检
make gate

# 启动本地依赖服务（PostgreSQL / Redis / MinIO）
make up

# 启动模型契约 Stub（端口 18000）
make stub
```

全部可用命令：

```bash
make help
```

| 常用目标 | 作用 |
|---|---|
| `make setup` | 建虚拟环境并装依赖 |
| `make gate` | 提交前必跑的门禁全量检查 |
| `make up` / `make down` | 启停本地依赖服务 |
| `make stub` | 启动模型契约 Stub |
| `make test-unit` / `test-contract` / `test-integration` | 分层跑测试 |
| `make gate-mutation` | 变异测试：故意改坏检查规则，验证检查真的会报错 |
| `make fmt` / `make lint` / `make type` | 格式化、静态检查、类型检查 |

> 配置本地环境变量：`cp deploy/compose/.env.example deploy/compose/.env`，然后填入真值。
> `.env` 已被仓库忽略，任何含口令的文件都不要提交。

## 七、部署形态

按数据敏感度分级，同一个产品支持三种部署形态：

| 形态 | 适用场景 | 关键要求 |
|---|---|---|
| **公有云** | 低敏感数据、小团队试用 | 数据加密、租户隔离 |
| **混合部署** | 中等敏感度 | 索引与元数据留在本地，模型可走云端 |
| **完全私有化** | 高合规行业（金融、政务、能源、医疗） | **数据不出域**；容器化一键部署，一周内完成 |

## 九、参与贡献

欢迎提交 Issue 与 Pull Request。

- **提交前请先本地跑通 `make gate`。** 门禁的设计意图是让问题在**你本地**暴露，而不是留到评审时才暴露。
- 提交信息建议采用 Conventional Commits 风格（`feat` / `fix` / `docs` / `chore` / `refactor`）。
- 修改内核层代码时，请先过一遍“五条工程纪律”——尤其是第 1 条。
- **不要提交任何真实业务数据。** 样本一律使用合成数据；`deploy/fixtures/` 只放合成件。
