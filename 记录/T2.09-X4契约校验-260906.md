## 二、五处发现与处置

### 发现 ①｜端口表三处与 §3.8 冻结表错位（判据源错误 · P0）

契约 X4.2 声称「交付默认（§3.8 冻结）」，但后三行与 §3.8 原文对不上：

| 变量 | v1.2 填的 | §3.8 实际 | 后果 |
|---|---|---|---|
| `API_HOST` | `8000` | Web/API = **8080**；8000 属**模型服务** | API 与模型服务抢 8000 |
| `MODEL_HOST` | `8100` | 模型服务 = **8000**；§3.8 无 8100 | 凭空造端口 |
| `VAULT_HOST` | `8080` | 8080 属 **Web/API**；§3.8 **未定义脱敏端口** | Vault 与 Web/API 抢 8080 |

三行像是连锁错位：先决定给 Vault 用 8080，再把 API 挪到 8000、模型挪到 8100。

**危害**：T3 实现、T8 部署手册、E1/E2 环境都照契约填。交付环境一旦按 v1.2 配置，**同时撞出两处端口冲突**，而报错只会表现为「连接被拒」，排查方向从一开始就错。

**处置**：按 §3.8 原文逐项订正；补回 §3.8 冻结但 v1.2 漏列的 `EMBEDDING_HOST`(8001)／`RERANKER_HOST`(8002)；新增「compose 落地」列——**契约列了 9 个变量，只有 5 个在 compose 里**，`VAULT_HOST` 属外部服务、`API_HOST` 在 E0 本机运行，此前无从分辨。

**`VAULT_HOST` 交付端口列为待拍板**，不擅自选定：§3.8 未定义脱敏端口——§四 明确「脱敏能力……由甲方安全团队提供既有产品或指定第三方产品」，端口随甲方产品而定。填任何具体值都可能与 §3.8 冲突。T8.02 前须闭环。

### 发现 ②｜部署步数错位：「十步」不是 §5.3 的步数（判据源错误）

§5.3 原文是**十二步**（第 11 离线验证、第 12 交接签字）。契约 X4.3 写「十步不许跳步」且自称权威依据 §5.3，但内容与 §5.3 只有前三步相同——多了 DDL 初始化/健康检查/冒烟，漏了能力注册/导入流程/导入样本/端到端/离线验证/交接签字。

**为什么门禁没抓到**：X4.5 判据写的是「部署手册含十步（手册 8 §T8.02）→ 有」。手册 8 确实有自己的十步（把第 11、12 步合并计入 T8.06/T8.07），判据因此 PASS。它查的是**存在性**，不是**一致性**——三份文件三套步数（§5.3 十二 / 手册 8 十 / 契约十），门禁全绿。

**处置**：按 §5.3 原文恢复十二步。第 7 步按 TR-3 去行业词（§5.3 原文作「企业信贷报告生成」，契约作为 EKOS 共用层文档写作「报告生成流程」，具体流程名走配置层），并在文中标注这是有意的合规改写而非漏抄。

### 发现 ③｜「密钥不入库」判据查错了对象（判据空转 · 关键）

原判据：

```
git grep -n "password\|secret" -- '*.yml' '*.yaml' | grep -v '${'
```

按**整行**过滤，只要行内含任意变量引用就整行放过。实测：

```
POSTGRES_PASSWORD:   ${PGPASSWORD:-ekos_dev_only}      ← 明文口令在 git 里
MINIO_ROOT_PASSWORD: ${MINIO_PASSWORD:-ekos_dev_only}  ← 明文口令在 git 里
```

这两行**自己就带 `${`**，于是从未报警。判据要查的是 `${VAR:-默认值}` 里**默认值本身**，不是这一行长什么样。

**处置**：
- compose 两处改为 `${PGPASSWORD:?…未设置}` / `${MINIO_PASSWORD:?…}`——缺变量时 compose 直接报错，优于静默使用弱口令；
- 新增 `.env.example`（模板，进 git，值全为 `change_me`）与本机 `.env`（真值，`.gitignore` 第 19 行已忽略，第 21 行 `!.env.example` 放行）；
- 本机 `.env` **沿用原值**：PG/MinIO 数据卷在首次初始化时就把口令写死了，改值会让已在运行的容器数据不可访问。本轮目的是「真值不进 git」，不是轮换开发口令。
- 判据改为自动化断言 `test_no_plaintext_secret_defaults_in_deploy_files`。

**顺带发现**：`deploy/scripts/backup_restore.sh` 里同样的明文默认口令，而**原判据的扫描范围只有 `*.yml`/`*.yaml`，脚本连被查的资格都没有**。更讽刺的是该脚本第 3 行写着「Secrets come from environment variables, never hardcoded in this script」——注释声明与实现完全相反。已改为缺变量即报错退出，并把扫描范围扩到 `**/*.sh`。

### 发现 ④｜备份脚本缺执行权限

实测 `./deploy/scripts/backup_restore.sh` 报 permission denied。一个不能执行的备份脚本等于没有备份能力，而门禁看不出来。已 `chmod +x`，并加断言 `test_backup_script_is_executable` 守住。

### 发现 ⑤｜一处需要更正的判断（避免虚报）

我在校验中途判断「开发端口避开冻结段这条判据不与 §3.8 比对，等于失效」。**注入变异实测后确认这个判断是错的**：把 compose 默认端口改成 `5432`，门禁 TR-7 立刻 FAIL——

```
[FAIL] deploy/compose/docker-compose.dev.yml:40 → compose 主机侧端口 5432 占用交付冻结段
```

所以真实情况是：**门禁 TR-7 一直是有效的，弱的是契约文档 X4.5 里那条手工 grep**。照文档执行的人以为只有手工 grep 这一道，形成「文档弱判据与门禁强实现长期脱节」。

这条已回写到契约 X4.5 与测试文件注释中。新增断言的定位也随之修正为**补充**而非从零发现：把扫描范围从编排文件扩到 `deploy/` 全部（含 `.sh`，TR-7 不扫脚本），并增加「是否落在开发段」检查（如 `17000` 既不属冻结段也不属开发段，TR-7 不报，本断言报）。

### 变异 3 为什么首版漏判（本轮最值钱的教训）

判据里我写了：

```python
host_side = entry.split(":", 1)[0]      # ← 错
for m in re.finditer(r":-(\d+)\}", host_side):
```

`"${PGPORT_HOST:-5432}:5432"` 按第一个冒号切，得到 `${PGPORT_HOST`——**变量默认值语法 `:-` 自带冒号，切分提前中断，默认值根本没被读到**。于是「把开发端口改成冻结端口」这个最该抓的变异，8 条断言全绿。

修法：变量形态先找到配对的 `}` 再切；默认值提取改成在整条上做。

**这与 T2.08 的两次漏判同源**：判据照着「我以为的写法」写，而不是照着**真实的字符串形态**写。T2.08 是漏了大写字面常量和字典字面量，这次是漏了变量语法自带的冒号。结论一致——**判据必须拿真实字符串试过才算数**。

### 另一处判据自身的坑

改 f-string 时发现：断言提示文字里含 `${VAR:-默认}`，f-string 与 `.format()` 都会把花括号当表达式解析。这两处改用字符串拼接，其余 11 处改 f-string。
