# CheersAI Vault 集成方案 v1.2

## 一、结论层

### 1.1 架构定位（本方案最重要的一条）

**EKOS 侧不实现脱敏算法，只实现 Vault 适配器。**

- 脱敏能力由 **CheersAI Vault 工程**（`subproducts/CheersAI-Vault`）提供，是 EKOS 的 MVP 内核功能与安全差异化内核。
- EKOS 仓库 `packages/vault/` 的正确身份是 **Vault Runtime API 的客户端适配器**（HTTP client + 编排 + 错误处理 + 测试），**不是**脱敏引擎。
- 依据 60.90.03 §四原文：

  > 脱敏能力是独立于云模型的安全服务，由甲方安全团队提供既有产品或指定第三方产品、规则和测试环境；**勤思负责开发适配器、调用编排、错误处理和测试，不承诺自研脱敏产品**。

- 依据同节交付物第 4 项：**「一个脱敏 API 适配器及测试报告」**。

> ⚠️ 纠错说明：此前 `packages/vault/service.py` 被实现为一套正则脱敏引擎（含 `masking_policy.json` 6 条自研规则），属于**重复造轮子**，方向偏离本方案。应改为适配器实现。

### 1.2 Vault Runtime API 能力边界（E0 实测，非推测）

部署形态：Rust / warp 服务，默认端口 `8787`，只监听 `127.0.0.1`，客户内网经 Nginx 反代访问。
E0 实测已启动本机 release 二进制，`GET /api/v1/health` → `{"status":"ready","version":"0.1.0"}`。

**客户测试首版承诺 4 项 API**（`docs/enterprise/API_REFERENCE.md`）：

| 接口 | 用途 | 实测 |
|---|---|---|
| `POST /api/v1/batches` | 批量提交多文件（multipart，单批上限 2GB） | ✅ 2 文件一次提交成功 |
| `GET /api/v1/batches/{id}` | 进度轮询与失败信息 | ✅ 终态 <1s 返回 |
| `GET /api/v1/artifacts/{id}` | 下载脱敏结果（Markdown） | ✅ 可取回 |
| `GET /api/v1/health` | 就绪检查 | ✅ ready |

**内置脱敏规则 7 条**（`GET /api/v1/rules` 实测）：
`id_card` / `phone` / `email` / `bank_card` / `ipv4` / `passport` / `use_sensitive_terms`（敏感词库）

### 1.3 能力对照表（EKOS 现有规则 ↔ Vault）

| EKOS `masking_policy.json` 规则 | Vault 对应 | 状态 | 处置 |
|---|---|---|---|
| `ID_CARD` | `id_card` | ✅ 原生 | 直接映射 |
| `PHONE` | `phone` | ✅ 原生 | 直接映射 |
| `EMAIL` | `email` | ✅ 原生 | 直接映射 |
| `BANK_CARD` | `bank_card` | ✅ 原生 | 直接映射 |
| `PERSON_NAME` | **无内置** → 敏感词库 | ⚠️ 配置层可解 | **走 `/api/v1/sensitive-terms` 配置，不自研 NER** |
| `USCI`（统一社会信用代码） | **无** | ❌ **缺口** | 信贷场景企业主体核心字段，需拍板（见第五节） |

Vault 额外提供但 EKOS 未用：`ipv4`、`passport`。

### 1.4 人名脱敏：走配置，不走代码（已实测验证）

此前判定「人名不脱敏」为 P0 并挂账「等 T3.02 自研 NER」——**归因与处置均错**。实测证明正确路径是**往 Vault 敏感词库加配置**：

```
加入敏感词库前：申请人张三，身份证 ***IDCARD***1，手机 ***PHONE***2   （3 实体，人名残留）
加入敏感词库后：申请人[人名]，身份证 ***IDCARD***1，手机 ***PHONE***2 （4 实体，人名已脱敏）
```

操作仅为：
```bash
curl -sS -X POST "http://127.0.0.1:8787/api/v1/sensitive-terms" \
  -H 'content-type: application/json' \
  -d '{"term":"张三","category":"人名","description":"..."}'
```
（`李四` 同样处理后，两文档实体数 3→4 / 1→2，人名均脱敏为 `[人名]`）

**结论：人名属 Vault 配置层问题，不是 EKOS 代码层问题。敏感词库支持 CRUD + CSV import/export，可批量配置。**

### 1.5 实测暴露的其他缺口

| 项 | 实测结果 | 影响 |
|---|---|---|
| 护照 `EA1234567` | ⚠️ `passport` 规则在列但**未命中** | 证件类字段需验证格式兼容性 |
| 地址「北京市朝阳区建国路1号」 | ❌ 无规则，原样残留 | 信贷场景常见，需评估是否纳入 |
| 产物格式 | 统一转 **Markdown** | 与 EKOS 文档解析链路需对齐 |
| 映射表 | Vault **不提供 `.cmap` 下载**；反脱敏走服务器内 `POST /api/v1/artifacts/{id}/restore`（不在首版承诺范围） | 见 1.6 |

### 1.6 与 X1 契约的阻抗失配（需对齐）

| 维度 | Vault API | EKOS X1 契约（v1.2） | 差异性质 |
|---|---|---|---|
| 调用粒度 | **文件批次、异步**（提交→轮询→下载） | **文本同步**（`/detect` `/mask` `/restore`） | 结构性差异 |
| 映射表 | 不出 Vault；EKOS 侧拿不到映射 | 「映射表留本地 Vault，只回 `mapping_ref`」 | Vault 方案**更安全**，但 EKOS 侧无法本地反脱敏 |
| 反脱敏 | 调 Vault `restore`（非承诺范围） | EKOS 侧 `/restore` | 依赖 Vault 未承诺接口 |

**影响最大的一条**：60.90.03 §四 要求「Prompt 片段：RAG 检索命中的原文在**出网前再次检测和脱敏**」——这是**文本级、低延迟同步**调用，Vault 首版**无对应接口**（只有文件批次异步）。

## 二、论证层（实测证据）

### A-① 为什么「EKOS 不自研脱敏」——方案原文依据

60.90.03 §四 第 333 行明确责任边界，交付物第 42 项明确只交付「适配器及测试报告」。EKOS 侧自研正则引擎，既重复造轮子，又造不出 Vault 已有的成熟度（Vault 支持 CSV/Excel/JSON/TXT/Word/PPT/PDF/Markdown 多格式、批量、可逆、词库加密）。

### A-② 为什么「人名挂账等自研 NER」是错的处置

- 现象对：人名确实未脱敏。
- 归因错：误判为 EKOS 引擎缺 NER，实为**上游 Vault 无内置人名规则**（实测 `GET /api/v1/rules` 7 条中无人名）。
- 处置更错：应在 Vault 侧通过敏感词库配置解决（已实测可行，见 1.4），而非在 EKOS 侧自研 NER——后者正是方案禁止的「自研脱敏产品」。

### A-③ 实测原始数据

健康与规则：
```
GET /api/v1/health → {"status":"ready","version":"0.1.0"}
GET /api/v1/rules  → id_card 身份证号 / phone 手机号 / email 电子邮箱 /
                     bank_card 银行卡号 / ipv4 IPv4地址 / passport 护照号 /
                     use_sensitive_terms 敏感词库
```

批次脱敏（2 文件，`rule_ids` 全开）：
```
batch.status = Completed（终态，1 次轮询内）
batch.masked_entity_count = 6（加敏感词后）；加之前 = 4
ekos-v-d1.txt: 4 实体 → 申请人[人名]，身份证 ***IDCARD***1，手机 ***PHONE***2，邮箱 ***EMAIL***3
ekos-v-d2.txt: 2 实体 → 联系人[人名]，银行卡 ***BANKCARD***1，护照 EA1234567，地址 北京市朝阳区建国路1号
```

### A-④ 部署形态约束

`deploy/linux/` 只提供 systemd + Nginx 方案（`vault-runtime-api.service`、`nginx-cheersai-vault.conf`、CIDR 白名单），**无容器化部署材料**（`docker/` 下仅有 `web-nginx.conf`）。
而 EKOS 首期 POC 为容器化（docker compose），Vault 需独立部署后由适配器跨进程调用。

## 三、集成设计（已实施）

### 3.1 改造目标

`packages/vault/` 由「正则脱敏引擎」改为「Vault Runtime API 适配器」：

```
EKOS 业务层
    ↓  X1 契约接口（/detect /mask /restore /health）
packages/vault/  ← 适配器：协议转换、规则映射、轮询编排、错误处理
    ↓  HTTP
CheersAI Vault Runtime API（/api/v1/batches 等）
```

### 3.2 规则映射表（适配器内维护）

```yaml
ID_CARD    → id_card
PHONE      → phone
EMAIL      → email
BANK_CARD  → bank_card
PERSON_NAME → use_sensitive_terms   # 依赖 Vault 侧敏感词库配置
USCI       → （缺失，待定）
```

### 3.3 配置项（走环境变量，不硬编码）

| 变量 | 说明 |
|---|---|
| `VAULT_API_BASE_URL` | 如 `http://127.0.0.1:8787/api/v1` |
| `VAULT_RULE_IDS` | 启用的规则 ID 列表 |
| `VAULT_POLL_INTERVAL_MS` | 轮询间隔（文档建议 ≥1s） |
| `VAULT_TIMEOUT_MS` | 超时（方案 §651：脱敏 API 超时 → 禁止云端调用，切本地或停止） |

## 六、实施结果（E0 端到端实测，非 fake）

适配器已落地，并用**真实 Vault 服务**跑通全闭环。

| 接口 | 实测结果 |

### 验证目标更正（2026-09-05 复核发现）

首轮验证时记录为「本机 release 二进制，端口 8787」，**该描述有误**：

- 8787 端口自 2026-08-05 起已被**在用容器** `cheersai-vault-runtime` 占用（映射 `0.0.0.0:8787->8787`）
- 手动启动的 release 二进制因端口冲突**未起来**（启动日志为空、进程不存在）
- 因此首轮所有实测实际打的是**在用容器服务**——结论依然成立（甚至更有价值：是真实容器化部署），但归因需更正

**由此暴露的更重要问题**：该容器是**生产级在用服务**（数据卷内有 7-8 月历史业务批次、敏感词库内有业务词条「智网数科」「管网」），拿它做测试靶子会写入持久化数据卷。已处理，见下。

### 隔离实例上的复验（2026-09-05，干净环境重跑）

| 阶段 | 结果 |
|---|---|
| 词库为空时 `mask` | `申请人张三，身份证 ***IDCARD***1，手机 ***PHONE***2，邮箱 ***EMAIL***3`；`entity_count=3`；**人名残留** |
| 同时 `health` | `status=degraded`，`rule:PERSON_NAME: config_dependent` —— **行为与报告一致，未静默** |
| 加入人名到敏感词库后 `mask` | `申请人[人名]，身份证 ***IDCARD***1，手机 ***PHONE***2，邮箱 ***EMAIL***3`；`entity_count=4` |
| `restore` | 完整往返还原 ✅ |
| `detect` | 4 实体：`PERSON_NAME[3:7]` / `ID_CARD[12:25]` / `PHONE[29:41]` / `EMAIL[45:57]` |

> 这组复验的意义：空词库时人名残留**不是缺陷**，而是「配置未就绪」的真实反映，且 `/health` 已如实上报。
> 这正是「规则生效完整性」纪律要达到的效果——**红光从看不见变成看得见**。

落地文件：

- `packages/vault/service.py`（重写）：正则引擎 → Vault 适配器；保留 X1 契约类型不变。
- `packages/vault/masking_policy.json`：自研正则规则表 → **Vault 规则映射表**（含 `lang` 列，TR-6 保留）。

**门禁全绿**：ruff / format / mypy 33 文件 / unit 20 / contract 11 / 六条常检 FAIL 0 → PASS。

### 过程中修掉的两个真实缺陷

1. **`health()` 漏捕 `VaultUnavailableError`**：Vault 不可达时接口直接抛异常崩溃，而非降级上报。已补捕获。
2. **TR-7 违规**：`client.py` 曾硬编码 `http://127.0.0.1:8787`。已改为 `VAULT_API_BASE_URL` 必填注入（无默认值），
   并把 `VaultService` 改为惰性创建客户端——否则 `api.py` 模块级构造会在未配置时直接崩在 import 阶段。

### 一条值得记住的教训

新增的「防造轮子」架构守卫（断言 `packages/vault/*.py` 不含敏感实体正则）**第一版是恒真的**：
用 `re.search(r"\d{17}[\dXx]", 源码)` 去找的是「17 个数字」，而源码里是字面七个字符 `\d{17}`，永远匹配不上，
于是注入一条自研正则后测试照样 PASS。**靠变异测试才挖出来**——又印证那句：看起来通过了，先问它到底查了没有。
已改为字面匹配，并补「扫描文件数非空」断言（glob 落空也会让守卫空过）。
