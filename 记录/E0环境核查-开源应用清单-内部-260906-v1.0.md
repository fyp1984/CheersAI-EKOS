## 附件 B · 高风险项展开

### B-① RAGFlow 底座：E0 的"能用"不等于 E1 的"能交付"（风险：高）

**结论**：E0 有 RAGFlow 实例，但它**不能作为交付能力的证据**。

**为什么是高风险**：结论反直觉——容器 `healthy`、接口返回 401（证明端点鉴权有效），看起来"已就绪"，但 T2.03 分工决策里 RAGFlow 承担三环（连接器 / 深度解析 / 三索引检索），这三环的可达性证据全部来自一个**他项目的 amd64 模拟实例**。

**依据与出处**：
- 镜像架构实测 `docker image inspect infiniflow/ragflow:v0.26.4` → `amd64 linux`（本机 arm64，经 Docker Desktop 模拟）。
- `记录/env-E0.md` 第 19 行已明确"性能/质量数字一律无效"，第 23 行"E1 必须用真实 x86_64 真机 + 官方镜像"。
- 「可建数据集」未实证：需 API Key，且该实例是在用试验环境，写入即污染（T1.07 挂账项）。

**防御措施**：分工决策表里加了"E0 实证状态"列逐环写实，并加断言**禁止把三环状态改成「已验证/已跑通」**——防的不是笔误，是伪造验收。

**答不上来的连带后果**：若甲方在 Q4 追问"三索引检索实测 Recall@8 多少"，E0 给不出任何有效数字，而 §3.5 三组指标是硬门槛（中→中 Recall@8 ≥90%）。

### B-② 模型权重：E0 只做了一个演示下载（风险：高）

**结论**：6 个模型里 5 个的 Revision 与 SHA-256 仍是"待 E1"，只有 bge-m3 做过一次演示下载（落 `/tmp/ekos-models`，非 `/data`，属临时目录）。

**为什么是高风险**：T1.06 判据是"每个权重 Revision + SHA-256，禁 latest"，现在 5 项为空。**这不是违约**（T1.06 属 Q5，未到期），但若被读作"已完成"就会在 Q5 突然暴露缺口。

**出处**：`记录/sha256-models.txt` 第 10-14 行；E0 演示段在 18-21 行（bge-m3 commit `5617a9f6…`，SHA `b5e0ce34…`）。

**连带后果**：`/tmp` 会被系统清理，演示权重不是可复现资产；E1 必须重下并复验。

### B-③ 三个许可证组件：正式商业交付前必复核（风险：高）

**结论**：PyMuPDF（AGPLv3）、MinIO（AGPLv3）、Redis 7.4+（RSALv2 + SSPLv1）都是**强传染性或非 OSI 许可**，MVP 阶段可用，正式对外交付前必须复核义务。

**为什么是高风险**：用户已授权"MVP 阶段可用 Redis/MinIO"，但 PyMuPDF 是**这次核查才进入清单**的第三项——它是 PDF 解析链路的核心依赖（§3.7 冻结 1.25.1），替换成本高于 Redis/MinIO。

**依据**：Redis 自 7.4 起改为 RSALv2 + SSPLv1 双许可（不再是 BSD-3）；MinIO 社区版 AGPLv3；PyMuPDF 1.25.x 为 AGPL-3.0。**以上须以各项目官方 LICENSE 文件为准核实**，核实命令：

```bash
.venv/bin/python -c "import fitz,os;print(os.path.dirname(fitz.__file__))"   # 找 PyMuPDF 包内 LICENSE
docker exec ekos-redis sh -c "ls /usr/share/doc/redis* 2>/dev/null | head"
```

**处置**：列入 T2.05 SBOM 的"许可证复核"列，Q6 交付前出结论；不因此改变本轮技术选型。

### B-④ 镜像 digest 只在台账、不在编排（风险：中）

**结论**：`image-digests.txt` 记了 4 个 digest，但 compose 文件里 `@sha256:` 命中数 = 0。

**为什么是中风险**：§3.7 明文"所有容器镜像使用不可变 Tag 和 Digest"。当前 Tag 已是精确三段（如 `0.8.0-pg16-bookworm`、`RELEASE.2024-11-07T00-52-20Z`），实际漂移风险低于用 `latest`；但 Tag 可被仓库重推，digest 不可。

**处置**：T3.09 部署包或 T7.06 供应链任务里，把 digest 写进 compose。
