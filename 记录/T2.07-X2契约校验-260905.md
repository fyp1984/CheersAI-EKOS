## 二、发现与处置

### ① 响应封套缺失（已修复，P0）

**现象**：契约 X2.4 要求响应为 `{request_id, document: {...}}`，实现直接返回裸 `ParsedDocument`。

**实测**（修复前）：

```
响应类型   = ParsedDocument
响应字段   = ['blocks', 'doc_id', 'language', 'parse_status', 'parser_version', 'source_uri']
>>> 契约要求含 request_id = False
>>> 契约要求 document 包装 = False
```

**为什么是 P0**：响应里**没有任何字段能标识这条结果对应哪一次请求**。同步调用尚可靠连接配对，一旦并发或重试，请求与结果就对不上，trace 链在解析这一步断掉。而 X2.3 明确写了 `parse_status`/`parser_version` 是「BIZ-1 可追溯与可重放的物理基础」——request_id 缺失，可追溯从源头就缺一环。

**判据来源**：不是我推断「应该带」。X1 的四个接口响应**全部**回传 `request_id`（契约 L85 / L107 / L127），X2 沿用同一纪律。所以是代码该跟契约走，不是契约写错了。

> 差异说明：X1 是平铺（`{request_id, entities, ...}`），X2 是嵌套（`{request_id, document}`）。两者都回传 request_id，形状不同是契约对 X2 的既定选择（解析结果结构复杂，嵌套更利于扩展），本次不改契约形状。

**修复**：`packages/document/api.py` 新增 `ParseResponse` 封套，`parse_endpoint` 改为返回 `{request_id, document}`。

### ② 解析层零测试覆盖（已补齐，根因级问题）

**现象**：`packages/document/` 在整个 `tests/` 下**零命中**——`tests/contract/` 只有 `test_model_contract.py`（X4 模型网关），X2 一条断言都没有。

对比：X1（脱敏）有 8 条断言，X2（解析）有 0 条。

**为什么这是根因**：① 那个响应封套缺陷，逐字段肉眼比对时是**全绿**的——字段一个不少，只是缺个包装。没有断言把它钉住，下轮重构随时可以再删掉。

**补齐**：新建 `tests/contract/test_document_contract.py`，19 条断言，覆盖 X2.2 / X2.3 / X2.4 / X2.5 / TR-3。

其中两条是**防自身退化**的守卫：
- `test_language_pattern_matches_contract_verbatim`：模式字面写在测试里，**不从 `schema.LANGUAGE_PATTERN` 导入**——导入等于让被测代码自己给自己发通行证，模式被改宽时断言同步放宽，永远成立。
- 两个 glob 守卫均带 `assert sources`（扫描文件数非空），防止 `glob` 落空导致守卫静默通过。

### ③ 契约 X2.3 描述过时（已同步，未升版本）

契约 X2.3 写「当前 `ParsedDocument` 缺以下两项……落地：`schema.py` 加可选字段」，但实测**两项都已存在**（`parse_status='ok'`、`parser_version='1.0.0'`）。

**处置**：更新 X2.3 现状描述为「已落地」。**未升版本号**——字段定义本身没变（契约原本就要求这两项），改的只是「是否已落」的状态描述，不构成实质性修订；与手册 02 只做指针同步时维持 v1.0 的处理方式一致。

不更新的代价：T3.03 会以为这两项待补，做无用功。

## 三、论证层（实测证据）

### 3.1 字段核对

```
doc_id           = 'minio://bucket/doc.pdf'
source_uri       = 'minio://bucket/doc.pdf'
language         = 'zh'
blocks           = []
parse_status     = 'ok'
parser_version   = '1.0.0'
```

`ParsedBlock`：`block_id` / `order` / `text` / `language` / `page` / `kind` 六项齐全，`page` 可空（`int | None`）。

> 附注：`parser.py` 骨架阶段 `doc_id = source_uri`。两者语义不同（资产唯一标识 vs 原始材料位置），真解析落地时须区分。骨架阶段相等可接受，已记入 T3.03 待办。

### 3.2 语种纪律（X2.5）

| 输入 | 结果 | 说明 |
|---|---|---|
| `zh` / `ko` / `zh-Hans` / `en-US` | 接受 | **加语种零改代码**——`ko` 能过是本条核心 |
| `ZH` / `z` / `zh-` / `zhongwen` / ` chinese` | 拒绝 | 开放不等于放任，格式须合法 ISO 639-1 |

默认值来源：`parser._load_default_language()` 读 `configs/runtime.yaml`，代码内无语种常量（守卫已钉住）。

### 3.3 TR-3 字段名扫描

```
扫描文件数 = 4
命中数 = 0
>>> TR-3 判定 = PASS
```

唯一与语种相关的命中在 `schema.py:18` 的**文档字符串**（「本模块刻意不写 `DEFAULT_LANGUAGE = "zh"` 这类常量」），是反面说明，非真常量。

### 3.4 变异验证（确认断言能抓住回归）

测试通过不等于测到东西。三组变异，全部被抓住：

| 变异 | 期望 | 实测 |
|---|---|---|
| 响应改回裸 `ParsedDocument` | FAIL | ✅ 2 条 FAIL（request_id / document 包装） |
| 代码写死 `DEFAULT_LANGUAGE = "zh"` | FAIL | ✅ 1 条 FAIL |
| 语种模式放宽为 `.*` | FAIL | ✅ 6 条 FAIL（含模式字面比对） |
| 全部还原 | PASS | ✅ 19 passed |

### 3.5 门禁 WARN 增量说明

常检 WARN 由 20 增至 22，新增全部来自新建测试文件：

- **中文字符串字面量**＝断言失败提示消息（`assert ..., "响应缺 request_id..."`），不是被写死的业务规则；
- **语种字面量**＝parametrize 参数（`"zh","ko","zh-Hans","en-US"`），正是契约要求验证的输入。

两者均在**测试层**，非共用层；与既有 `test_language_reservation.py` 的同类 WARN 性质一致（T2.04 已人工签字为确认性提示）。**本期确认：非违规。**
